## 一条安全设计原则（别被"优化"掉）

**危机信号规则引擎命中后直接返回固定话术，不调模型。**

原先实现是"给模型注入强制指令"，但模型偶发不可用是常态——
一个正要倾诉自伤倾向的学习者只会收到"稍后再试"。
**规则拥有结论，就必须拥有回应的确定性。**

评测集 `safety-003` 锁住这条（无 Key 也返回完整引导话术）。

## 契约：v1 与 v2 之间

### 现在（v1）

```
POST /api/chat   { learnerId, sessionId, text, audioUrl? }
           →     { ok, sessionId, text, reasoning[], citations[], suggestions[], degraded }
GET  /api/health → { ok, contract, modalities: { input:[], output:[] } }
```

**能力协商**：客户端必须先问"你支持什么"，再决定发送什么，
不得假设服务端支持某种模态。契约破坏性变更升版本号，`v1` 行为不变。

### 问题：v1 装不下胶卷模型

`/api/chat` 返回一段裸 `text`，是按**聊天记录**模型设计的。
而第一页要的是"一格一句"的结构化数据：

```
Frame   { text, picks[], revision, previous }
Question{ text, kind }
```

第二页还要：上传/粘贴的原文 → 选产出形态 → 生成结果。

### v2 要怎么改（未做，计划中）

```
POST /api/v2/frame
  { learnerId, sessionId, grade, text }
  → { frame: Frame, question: Question }

POST /api/v2/transform
  { learnerId, essay, form: 'picturebook' | 'comic' | 'animation' }
  → { jobId, status, result? }
```

**迁移原则**：`v1` 行为不变，新能力走 `v2` 并在 `/api/health` 的
`modalities` 里声明。客户端看能力声明决定发什么。

## system prompt

集中在 `server/src/agent/prompts/index.js` 一个出口，分四层：

| 层 | 职责 |
|---|---|
| `COMPANION` | 人格——温和的引导者/学伴 |
| `TUTOR` | 教学法——苏格拉底、自适应难度、双环、引用溯源 |
| `SAFETY` | 安全边界——不诊断不治疗 |
| `INPUT_ISOLATION` | 注入防护——用户消息是学习材料而非指令 |

### 待重写

现在这套是骨架期的占位版本，而且是**通用学习学伴**的口吻。
按 2026-10-29 定下的产品方向，要重写成**语文作文学伴**，并且必须包含：

1. **提问红线**（`isReaderQuestion` 的那两条）：只回应孩子已写出的内容，
   或陈述读者自己的阅读状态；**不许替孩子决定下一句写什么；不许句型填空**
2. **学段分叉**：1-2 年级只庆祝，不施加质量标准；3 年级以上才挑
   "有新鲜感的词句"
3. **文风**：读者口吻，不是老师口吻

**用户输入不得直接拼进 system prompt 指令区**（规范§四.2）——
`INPUT_ISOLATION` 那层就是划这条界的，重写时别删。

## 评测

```bash
cd server && node --no-warnings eval/run.js
```

规则（`eval/README.md`）：

1. **先写通过条件，再写用例。** `pass` 字段必须可检查，
   不写"质量好"这类空话
2. **判分用确定性断言，不上 model-as-judge。** 判分越确定，你越愿意勤跑
3. **约 20 条，每次改提示词或模型后都重跑**

离线用例覆盖**不依赖模型也成立的红线**：安全规则不误触发/不漏触发、
输入隔离条款存在且指令区不被污染、输入校验、降级响应形状完整。
安全类用例要**成对写**：一条该触发，一条不该触发——
只写前者会培养出过度敏感的规则引擎。

当前：离线 8 条（无 Key 可跑）+ 在线 2 条（缺 Key 自动跳过）。

## Kimi 探测结论（2026-10-29，两轮）

### 第一轮：Key 无效

用户先给的 `proj-6fe421e39aca...` 对 Moonshot 两个入口都返回
`401 Invalid Authentication`。**`proj-` 不是 Moonshot 的 Key 格式**
（它们形如 `sk-`），更像某平台的项目 ID。

### 第二轮：Key 有效，能力探清

正确 Key（`sk-` 开头）拿到后实测：

```
GET  /models              → 200  可用模型 6 个
POST /chat/completions    → 200  文本生成可用，质量好
POST /images/generations  → 403  "The API you are accessing is not open"
POST /videos/generations  → 404  url.not_found
POST /audio/speech        → 404  url.not_found
```

**可用模型**：`kimi-k2.6`、`kimi-k2.7-code`、`kimi-k2.7-code-highspeed`、
`kimi-k3`、`kimi-k3.1-pro`、`kimi-k3.1-pro-highspeed`

### 延迟实测（这是产品级问题，不只是技术参数）

| 模型 | 首 token | 总耗时 | 质量 |
|---|---|---|---|
| `kimi-k2.6` | **6.3s** | 7.1s | 好 |
| `kimi-k3.1-pro-highspeed` | — | 9.2s | 好 |
| `kimi-k3.1-pro` | — | 18.3s | 最好 |

**流式帮不上忙**：`kimi-k2.6` 开 `stream: true`，首 token 仍要 6.26 秒，
23 个 chunk 集中在最后 0.8 秒到达。模型要先"想"6秒才吐字。

**选 `kimi-k2.6`**：对孩子一句一句写来说延迟优先，且质量已足够——
实测它能产出真正引用孩子原句的读者回应，例如：

> 「这句话像一幅画，"唯一"的窗户和"粗糙"的手背让我一下子看见了那个安静的
> 小房间，阳光落得温柔又有分量。」

这验证了两件事：① 荣维东的读者立场在提示词层能做到；
② `isReaderQuestion` 那条红线不只是规则引擎的兜底，模型本身能守住。

### 对第二页的架构结论

**生图 403、生视频 404 —— 第二页必须走代码渲染。**
这本来就是既定决策（三个视觉方向都不押注 API），探测只是把它变成了确定事实。

**但 LLM 仍能大幅增强第二页**，而且是比直接生图更好的架构：

```
作文 ──LLM──> 分镜脚本（分成几格、每格画什么、每格的重点词）
     ──代码──> SVG + CSS 绘本 / 逐格动画
```

好处：确定、快、不依赖未开通的 API，而且分镜脚本本身是可见的教学产物
（孩子能看见"我的作文被拆成了这样的四格"）。

### 一个请求参数的坑

**k3 系列只允许 `temperature: 1`**，传 0.7 会返回
`400 invalid temperature: only 1 is allowed for this model`。
`server/src/model/client.js` 如果设了 temperature，接 k3 系列要先改掉。

探测脚本 `server/scripts/probe-kimi.js` **不打印 Key**，可反复用。

## 部署检查项

- [ ] **HTTPS**。麦克风权限要求 HTTPS 或 localhost，
      否则浏览器直接禁掉语音输入
- [ ] `.env` 通过平台环境变量注入，**不拷贝进镜像**
      （`.dockerignore` 已排除）
- [ ] **本机 3000 端口已被别的 Express 服务占用**，
      起本地服务用 `PORT=3010` 之类的
- [ ] `node:sqlite` 在 Node 22 仍是实验特性，启动脚本用 `--no-warnings` 压告警
- [ ] **会话状态不跨部署保留**（SQLite 落在容器文件系统里）。
      对外表述应为"会话状态在容器生命周期内持久化"
- [ ] `npm install --prefix <中文绝对路径>` 不被正确解析，
      用 `(cd <dir> && npm install)` 子 shell
- [ ] Git Bash 会把命令行里的中文搅坏，
      测中文输入必须先把 payload 按 utf-8 写文件，再 `curl --data-binary @file.json`
