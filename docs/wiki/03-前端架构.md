# 03 · 前端架构

`client/`，React 18 + Vite 6，**不用 TypeScript**，ESM。
CSS 用普通样式表（不用 CSS-in-JS、不引 Tailwind）——动效需要关键帧，
样式表是最直接的工具。**不引动画库**：一次性的位移动画用 FLIP 就够
（`lib/flyTo.js`），为它加一个依赖不划算。

    ├── api.js                      # checkAccess / unlock / analyzeEssay / askReader

    │   ├── highlight.js            # 范文正文里的词标注（markSegments）
    │   ├── moveBook.js             # 招式收藏册（localStorage）
    │   ├── letterStore.js          # 读者的回信（localStorage，上限 60 封）
    │   └── track.js                # 行为埋点：批量、静默失败、只计数不带身份
    └── components/
        ├── Gate.jsx                # 访问门槛：一个输入框，不记身份
        ├── StartScreen.jsx         # 第一拍：开始（跑马灯 + 一个大按钮）
        ├── StageGate.jsx           # 第二拍：选年级（3-6）

        ├── FlowWash.jsx            # 一层缓慢横移的光带，让屏幕"活着"
        ├── Analyzer.jsx            # 主界面：选范文 → 拆解 → 用一招
        ├── EssayPicker.jsx         # 阶段一：内置 79 篇 / 贴一篇自己的
        ├── EssayPane.jsx           # 范文正文（逐段，比对时忽略空白）

每个组件配一个同名 `.css`，由组件自己 import。样式不集中到一个大文件——
改一个组件不该打开全部样式。**关键帧也住在组件自己的样式表里**，
`app.css` 只留 `html.motion-off` 一条全局退路。

## 数据流

```
App (access, started, grade)
 ├─ Gate         access.required && !access.unlocked
 ├─ StartScreen  !started
 ├─ StageGate    grade === null
 └─ Analyzer     grade                     ← 主界面，阶段状态全在这里
     ├─ EssayPicker   onPick → runAnalyze
     ├─ EssayPane     essay
     ├─ MoveCards     analysis.moves, activeMoveId, onUseMove, onCollect
     ├─ ChallengeCard analysis.challenge, onSpotted
     └─ TaskDock      activeMove, grade, essay, onWritten
```

**没有路由库**，页面靠 state 四元切——五屏的产品引一个 router 是净成本。
`?grade=3..6` 跳过前两拍、`?essay=<id>` 直接开到拆解，都是录屏和评审用的深链，
不改变产品流程。

**Analyzer 是唯一有复杂状态的地方**：`essay / analysis / basis / precomputed /
attempts / status / error / activeMoveId / book / bookOpen / letters /
letterOpen / letterIndex`。三个阶段在一页里推进不跳路由，是因为从"看懂"到
"动手写"之间每多一次页面切换，就多一个放弃点。状态散开就会出现竞态。

册子（`lib/moveBook.js`）和回信（`lib/letterStore.js`）跨组件共享，通过 Analyzer
的 state 下发，写入统一走 `addMove` / `addLetter`——不要有第二个写入点。
两者都是 localStorage，都不过服务端。

**回信模态的开关也在 Analyzer**，因为它要同时服务两个入口：TaskDock 的
「再看这封回信」和顶栏的回信按钮。FLIP 的起点元素用 ref 传进去
（`letterAnchorRef`），关上时焦点还原给它。

## 埋点（只计数，不带身份）

`lib/track.js`。**权威的事件清单在 `server/src/analytics.js` 的 `EVENTS` 白名单里**，
两边必须对得上，加事件时两边一起改。

四条约束：

1. **绝不抛异常、绝不拦交互。** 埋点是附属功能，它没有资格让孩子的点击失败。
   所有失败路径静默吞掉。
2. **批量发送**：10 条或 2 秒一批。一次漏斗要走七八步，一步步发是七八个请求。
3. **会话 id 是随机数**，不由任何个人信息派生，只活在 `sessionStorage` 里——
   关掉标签页就换一个。唯一用途是让服务端算漏斗。
4. **不传任何原文**：孩子写了什么、范文是哪篇，一律不进入这里。

页面卸载时用 `visibilitychange` 而不是 `unload`——移动端和现代浏览器
常常根本不触发 `unload`，而切到后台一定触发 `visibilitychange`。

## 动效

全部 `cubic-bezier` 过冲，禁用 linear/ease 的"默认感"——
孩子的产品里东西要"啪"地到位，不要"渐"地出现。

| 动效 | 关键帧 | 在哪 |
|---|---|---|
| 招式卡一张张发出来 | `move-deal` | `MoveCards.css` |
| 贴纸持续往下落 | `scatter-fall` | `StickerLayer.css` |
| 读者回信"展开" | `letter-unfold`（`scaleY(0.55) → 1`，像把对折的信打开） | `TaskDock.css` |
| 等待态末尾的笔尖 | `pen-blink` | `TaskDock.css` |
| 册子"咚"一下 | `an-punch` | `Analyzer.css` |
| 依据卡进场 | `basis-in` | `Analyzer.css` |
| 加载条爬行 | `an-crawl` | `Analyzer.css` |
| 跑马灯（40 秒） | `start-roll` | `StartScreen.css` |
| 光带横移 | `flow-wash` | `FlowWash.css` |
| 放大镜浮动 + 镜片扫光 | `magnifier-float` / `magnifier-sweep` | `Magnifier.css` |
| 飞牌 / 飞便签 | FLIP + transition，不用关键帧 | `lib/flyTo.js` |

**动效常开，不跟随系统"减少动态效果"偏好。** 动效是这个产品的内容不是装饰——
落贴纸、发牌、那句飞进作文本全是反馈本身。曾做过一个听系统的开关，
但那个开关在"只是顺手关掉 Windows 动画效果"的机器上会让产品看起来是坏的。
`html.motion-off` 那套规则保留着当无障碍退路，**别删**。

## 三个踩过的坑（别再犯）

### 1. FLIP 动画必须等下一帧再设终点

`lib/flyTo.js`：先把 ghost 定位到起点并 `appendChild`，然后在
`requestAnimationFrame` 里才写 `transform`。同一帧里写起点和终点，
浏览器只会看到终点，动画根本不动。

### 2. 粘贴进来的范文没有 id，册子会串

招式 id 是 `m1/m2/m3` 按次生成的，而册子的键是 `essayId::moveId::from`。
两篇不同的粘贴范文共用一个假 id 的话，会互相把对方的 `m1/m2/m3`
当成自己收过的。所以 `withEssayId` 每贴一篇就发一个真 id，
重试时沿用同一个。

### 3. 无头截图验不了动画时钟，窄 viewport 下还会骗人

`currentTime` 停在 0，"动画到底动不动"只能由用户亲眼确认，
**不要报告成已验证**。另外本机 DPI 144 / 缩放 1.5 会让
`--window-size=390,844` 实际渲染得更宽再裁掉右侧，
看起来跟布局横向溢出一模一样，`--force-device-scale-factor=1` 也治不了。

**正确的验证方法**：写一个临时 HTML 用 `<iframe style="width:390px">` 加载页面，
读 `contentDocument.documentElement.scrollWidth` 和各容器的
`getBoundingClientRect().width` / `scrollWidth`。
`docScrollW === 视口宽` 就证明没有溢出。用完删掉临时文件。

截图统一走 `node "D:/比赛/.claude/skills/oil-ui/scripts/shoot.mjs" <url> --size 1440x900`，
**不要用 windows-mcp 拉 Edge**——用户的 Edge 以管理员权限运行，会弹权限模态框
且非提权进程点不掉。

**改完前端要截图前，先确认 `dist` 比源码新**——`express.static` 直接读 dist，
拿旧产物的截图当验证这件事真犯过。

## 字体：为什么是幼圆 + 0.7px 描边

本机实测四款中文字体 × 五种描边厚度（截图在 `.oil-ui/writing-agent-directions/shots/round2/14、15`）：

| 方案 | 问题 |
|---|---|
| 幼圆原生 | 唯一可用的圆体，但只有 regular 一档，700 是伪粗，撑不起"主角" |
| 微软雅黑 Bold | 有真粗，但笔画太粗，**把后面的黄色荧光笔压得看不见** |
| 华文楷体 | 有语文/字帖的味道，但是书法体不是圆体，伪粗很难看 |
| 黑体 SimHei | 最重最硬，像政府标语 |
| 幼圆 + 1.4px 描边 | 笔画糊在一起 |
| **幼圆 + 0.7px 描边** | ✅ 既圆又有分量，荧光笔还在 |

```css
--font-round: 'YouYuan', '幼圆', 'Yuanti SC', 'STYuanti', 'Microsoft YaHei', sans-serif;

.screen-text {
  font-family: var(--font-round);
  -webkit-text-stroke: 0.7px currentColor;
}
```

**换机器部署先确认目标机器有幼圆**（Windows 有，macOS 对应 Yuanti SC）。
没有就会退到微软雅黑——那时要把描边降到 0.4px，不然太厚。

Fredoka（自托管 29KB）仍用于英文与数字，和幼圆同属圆体，混排不冲突。
