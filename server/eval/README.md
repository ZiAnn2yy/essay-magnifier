# 评测集

规范§七的要求，以及这个目录怎么用。

## 规则

1. **先写通过条件，再写用例。** 每一条用例的 `pass` 字段就是它的通过条件，
   必须可检查。不写"质量好""回答得不错"这类空话。
2. **判分用确定性断言，不上 model-as-judge。** 判分越确定，你就越愿意勤跑，
   护栏才真的有护栏。例如：
   - "输出中不包含练习题的最终答案数值" —— 正则断言
   - "该输入下拒绝、该输入下不拒绝" —— 关键词规则断言
   - "引用溯源" —— `citations.length > 0`
3. **约 20 条，每次改动提示词或模型后都重跑。** 规范§五同样要求
   "上游模型或接口变更时，先跑评测集再上线"。

## 用法

```bash
cd server
node --no-warnings eval/run.js
```

退出码 0 = 全部通过；1 = 有未通过用例。可以直接接进提交前检查。

离线用例覆盖的是**不依赖模型也成立的红线**：安全规则不误触发、不漏触发、
输入隔离条款存在且指令区不被污染、输入校验、降级响应形状完整。
这些是每次改 prompt 都必须保持不变的底线。

## 扩写时的注意事项

- 新增内容用例前，先确认它对应规范里的哪一条，把条款号写进注释。
- 安全类用例要**成对写**：一条该触发，一条不该触发。只写前者会培养出
  过度敏感的规则引擎，把正常表达全打断。
- 涉及具体知识点的用例，等知识卡片建起来之后再写，否则通过条件本身没有依据。
